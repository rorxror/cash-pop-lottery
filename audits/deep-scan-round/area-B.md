# DEEP SCAN — AREA B: Backend Correctness (READ-ONLY, no files edited)

[B-01] GALTI — BP-22 auto-approval double-counts its own withdrawal in the daily/monthly cap re-check, so auto-approve silently dies for amounts over half the cap — lib/money.js:488 `const rules = await checkWithdrawalRules(db, s, user, method, w.amount, decodeUserData(w.user_data));` combined with lib/money.js:301 `if (Number(row.s) + amountMinor > dailyCap)` (same pattern :306 monthly), where the SUM at :300 is over `status IN ('pending','approved','paid')` — the withdrawal being re-checked is already 'pending', so it is counted in `row.s` AND again as `amountMinor`. At creation the same check runs before INSERT (correct); at auto-approve time it does not. Example: cap $500, single $300 withdrawal → re-check computes 300+300=600 > 500 → `rules_blocked`. Impact: fail-safe (stays manual, no money moves), but BP-22 is broken for a large part of its intended range with no visible reason (the reason string is only in the function's return value, never logged).

[B-02] GALTI — Admin KYC approve/reject have no guarded transition and unconditionally overwrite the user's KYC status — routes/admin.js:1946-1947 `UPDATE kyc_documents SET status = 'approved' … WHERE id = ?` / `UPDATE users SET kyc_status = 'verified', kyc_note = '' WHERE id = ?` and :1958-1959 (reject → `'rejected'`). The only protection is a pre-read `doc.status !== 'pending'` check (:1945/:1955) with awaits between read and write, unlike deposits/withdrawals which use `WHERE status='pending'` + changes-check. Two admins deciding concurrently both "succeed"; worse, decisions are per-document but status is per-user: approve doc B (user verified), then reject still-pending older doc A → user becomes 'rejected' and loses verification doc B earned. Impact: wrong KYC state gating real withdrawals/deposits; audit log records two contradictory "successful" decisions.

[B-03] GALTI — Player KYC resubmission unconditionally downgrades a verified user, and the upload endpoint has no rate limit or submission cap — routes/player.js:544 `router.post('/kyc', requireLogin, async …)` (no `rateLimit(...)`, unlike /deposit/new at :290 and /play/buy at :54) and :555 `await req.db.run("UPDATE users SET kyc_status = 'pending' WHERE id = ?", [req.user.id]);` with no status precondition. Any verified user (or a hijacked session) submitting one more document instantly loses verified status; unlimited 5 MB submissions each write a file via `storeUpload` (routes/player.js:552) with no per-user count limit. Impact: verification-loss on resubmit + authenticated disk-fill DoS on the private KYC store.

[B-04] GALTI — BP-23 scheduled-launch guardrail fails OPEN on error, and scheduled launch failures are swallowed with zero trace — lib/scratch.js:370 `} catch {}` closes the block containing `seriesExposure`/`launchCapCheck`, after which execution falls through to launch; :371 `try { await launchSeries(db, r.id, null); out.activated += 1; … } catch {}`. If the exposure/cap computation throws, the series launches unguarded; if `launchSeries` itself throws, there is no audit row, no scratch_event, no error count — the cron job reports "ok" and the same draft retries every 5 minutes forever, invisibly (contrast the cap-blocked branch at :364-368, which does log). Impact: the headline BP-23 launch cap is bypassable by an internal error, and a permanently broken scheduled series looks healthy in the Automation Console.

[B-05] GALTI — Smart auto-next is single-shot per tick, unguarded, and non-atomic — lib/scratch.js:423 `if (endedNow.length && getBool(settings, 'scratch_auto_next_enabled', false))`, :445 the smart pool is computed only from `endedNow[0]`, and :457-466 the clone INSERT and tier INSERTs run as separate statements followed by a bare `await launchSeries(db, r.id, null);` with no `launchCapCheck` (the cap manual launch at routes/scratch.js `/​:id/launch` and scheduled launch both enforce). If two series end in the same tick only one clone is ever created — `endedNow` is only populated on the transition tick, so the second series' auto-next is lost permanently. If `launchSeries` throws on the clone, an orphan draft with `launch_at = NULL` remains that no later lifecycle run will ever launch, and the exception aborts the rest of `scratchLifecycle`. Impact: silently missing replacement series, a BP-23 cap bypass path, and partial lifecycle state.

[B-06] KAMZORI — Multipart parser silently truncates files and lets embedded parts overwrite fields (verified by execution) — lib/upload.js:41-43 `let bodyEnd = buffer.indexOf(boundary, bodyStart); … bodyEnd -= 2; // strip the CRLF before the boundary` and :56 `fields[name] = body.toString('utf8');`. Executed proofs: (1) a file whose bytes contain the boundary sequence parsed to a 3-byte file and the fake part embedded in the file content overwrote `fields.doc_type`; (2) a closing boundary not preceded by CRLF stripped 2 real file bytes. The magic-byte check in `validateUpload` inspects only the header bytes, so a truncated/corrupt JPG/PDF passes and is stored as a genuine pending KYC document. Exploitability is limited (the boundary is client-chosen and normally random in browsers), so impact is corrupt-document acceptance rather than a gate bypass.

[B-07] KAMZORI — KYC multipart middleware consumes unbounded oversize streams and runs before authentication — server.js:283 `req.on('data', (c) => { size += c.length; if (size > KYC_MAX_BODY) { tooBig = true; chunks.length = 0; } … })`: after the cap trips it keeps draining the request to completion instead of aborting, so body size/duration are unbounded (only memory is capped); the middleware is an `app.use` that executes before the routers, so an unauthenticated client can force repeated 6 MB read+parse cycles on POST /kyc before `requireLogin` ever runs. Cosmetic companion: server.js:285 reports `maximum 5 MB` for a 6 MB body cap.

[B-08] GALTI — Unguarded `.trim()` on destructured body fields 500s on type-confused input — server.js:159 `express.urlencoded({ extended: true, limit: '2mb' })` (qs parsing turns `subject[x]=1` into an object) vs routes/player.js:815 `const { subject, message } = req.body;` → :821 `subject.trim().slice(0, 255)` and :823 `message.trim()…`, guarded only by truthiness. `POST /support/new` with `subject[x]=1` throws TypeError → wrapAsync → the global 500 handler, instead of a clean 4xx. Same pattern at routes/player.js:601-602 (`name.trim()` in POST /profile), routes/auth.js:330 (`name.trim()` in register), routes/agent.js:113 (`name.trim()` in agent player-create). Impact: authenticated/anonymous bad input produces 500s and error-log noise on four endpoints; no data corruption.

[B-09] KAMZORI — A cron job with no handler is recorded as a successful run, forever — lib/cron.js:147 `const msg = fn ? await fn(ctx) : 'no handler';` followed by the UPDATE that sets `last_status = 'ok'` with that message; lib/migrations.js:1119-1122 only INSERTs missing CRON_JOBS rows and never prunes/validates DB rows against code. Today code↔seed match (see coverage), but any stale/renamed handler_key row left in an existing production DB after a future deploy would show green in the Automation Console while doing nothing. `runNow` (:174) does throw for a missing handler — only the scheduled path lies.

[B-10] KAMZORI — Draw-exposure alert threshold hardcodes 2-decimal minor units and compares one number against every currency — lib/cron.js:22 `const threshold = toMinor(getS(settings, 'draw_liability_alert', '0'), 2) || 0;`, while `drawExposure` (lib/prize-engine.js) returns per-currency liabilities in each currency's own minor units. For a 0-decimal currency the threshold is inflated 100× (alert never fires); for a 3-decimal currency it is deflated 10× (alert spam); a EUR draw's liability is compared 1:1 against a USD-typed threshold with no conversion. Impact: BP-23(e) alerting only — settlement math is untouched — but the operator's liability early-warning can be silently absent exactly for non-USD draws.

[B-11] GALTI — Threshold-mode draw with threshold 0 is a reachable configuration that locks a draw (and its stakes) forever — routes/admin.js:586 `const num = (v, dflt) => { const n = parseInt(v, 10); return Number.isInteger(n) && n >= 0 ? String(n) : dflt; };` accepts `draw_threshold_* = 0` and it is saved at :592, while lib/draws.js:147/188 parse it back with `|| 0` and both settlement paths require `threshold > 0`: `settleDueDraws` in threshold mode only extends `close_at` +1h, and `checkThresholdDraws` skips `threshold <= 0`. A DAY/EVE type set to mode 'threshold' with threshold 0 never settles, never rolls with notice, and its entries stay 'pending' indefinitely until an operator notices and cancels manually.

[B-12] KAMZORI — Withdrawal cap re-check inside createWithdrawal is not actually race-proof on Postgres/MySQL — lib/money.js:300-306 reads `SUM(amount)` with no row lock / FOR UPDATE (contrast `settleAgentCommissions`, which uses `lockSuffix`), so under READ COMMITTED two concurrent creates for one user can both pass the daily/monthly cap and both insert. The shipped SQLite driver serialises via BEGIN IMMEDIATE, so this is not exploitable in the current deployment; it becomes live if the Phase-2 Postgres migration happens. Same check-then-act shape, lower stakes: the responsible-play daily deposit limit at routes/player.js:312 is checked entirely outside the deposit insert, so parallel deposits from one user can exceed their self-set limit even on SQLite (self-harm limit only).

[B-13] SUSPECT — KYC gate is enforced only at deposit creation, never at credit time — routes/player.js POST /deposit/new checks `kycBlock(..., 'deposit')`, but the webhook approval path (routes/webhooks.js, `decideDeposit(..., 'approve', …)`) and admin approval contain no KYC re-check, so a deposit created while KYC was off (or for a then-exempt user) is credited after the gate is switched on / the override flips to 'required'. Proof needed: operator intent — whether BP-21's gate is a creation-time gate (current behaviour defensible) or a credit-time gate (webhook path is then a bypass). No code evidence either way; flagged, not asserted.
